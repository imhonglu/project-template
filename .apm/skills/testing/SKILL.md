# 테스트 설계·작성

기존 테스트 도구·파일 관례를 유지하고, 없는 곳에는 아래 기본값을 적용합니다. Vitest API를 적용할 때는 [공식 문서 색인](https://vitest.dev/llms.txt)에서 설치 버전의 동작을 대조합니다. 테스트 도우미에 맞추려고 제품 API의 비동기·수명 계약을 바꾸지 않습니다.

## 작업별 기준

### 범위·파일 선택

요구사항·공개 계약에서 정상·경계·실패 사례를 정하고 기존 테스트와 대조합니다. 검증 계획에는 사례별 입력·조건, 기대 결과, 실제로 사용할 의존성과 격리 방법을 적습니다.

| 검증할 계약                        | 선택할 수준·파일명 예                           | 읽을 예제                                      |
| ---------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| 외부 자원 없는 계산·분기·상태 전이 | 유닛: `get-shipping-fee.test.ts`                | [유닛 테스트](references/unit-tests.md)        |
| 실제 저장·조회, 모듈·DB·HTTP 연동  | 통합: `save-note.integration.test.ts`           | [통합 테스트](references/integration-tests.md) |
| DOM·이벤트·브라우저 API            | 브라우저: `create-cart-counter.browser.test.ts` | [브라우저 테스트](references/browser-tests.md) |
| 공개 API의 타입·추론               | 타입 단언 병행: `first-item.test.ts`            | [값과 타입 검증](references/type-tests.md)     |

- 테스트는 검증할 구현 가까이에 둡니다. 같은 대상·실행 환경은 한 파일에 모으고, 책임·격리·실행 비용이 다를 때만 나눕니다.
- 새 테스트는 `.test.ts`를 기본으로, JSX를 쓰면 `.test.tsx`를 사용합니다. 기존 `.spec` 등 도구에 연결된 관례는 유지합니다. 타입 단언도 일반 테스트 파일에 두며 별도 타입 테스트 전용 접미사는 만들지 않습니다.
- 브라우저 테스트는 브라우저 프로젝트에서만 수집되도록 `include`·`exclude`를 맞춥니다. 구체적인 파일 포함·실행·타입 검사 절차는 [값과 타입 검증](references/type-tests.md#파일-포함과-검사-명령)을 따릅니다.

### 사례 작성

사례별 입력·응답·옵션과 기대값·단언은 테스트 본문이나 바로 보이는 데이터 표에 둡니다. 도우미 안의 기본값이나 숨은 단언을 읽어야만 사례를 이해할 수 있게 만들지 않습니다.

- `describe`는 대상, `it`은 조건과 결과를 나타냅니다. 준비·실행·단언은 빈 줄로 구분합니다.
- 입력만 달라지면 `it.each`·`it.for`를, 시나리오가 다르면 별도 `it`를 사용합니다.
- 한 테스트는 하나의 시나리오를 다루고, 그 결과를 확인하는 단언은 함께 둡니다.

### 준비·격리

검증 대상은 실제 구현을 사용합니다. 범위 밖 의존성의 실패·완료 순서를 재현하거나 외부 상태를 격리해야 할 때만 대체합니다.
대체 구현은 사례에 필요한 동작만 제공합니다. 계산·변환은 모킹 응답의 단순 반환이 아니라 실제 공개 결과로 검증합니다. 오류 전달 계약은 원래 오류 자체를 단언할 수 있습니다.
시간·난수는 재현 가능한 값이나 시드로 통제하고, 가변 입력·모킹·DB·파일·포트는 사례별로 격리합니다.
자원을 얻은 직후 수명에 맞는 정리 작업을 등록합니다. 준비·종료가 실패해도 실제로 자원이 회수되는지 확인합니다.

| 필요한 처리                               | 참고할 기준·예제                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 테스트 본문에서 Disposable 자원 사용 완료 | `using`·`await using`; [파일 I/O 예제](references/integration-tests.md#실제-파일에-저장한-메모-다시-읽기) |
| 공통 준비·공유 자원·정리 순서             | [수명과 훅 선택](references/integration-tests.md#수명과-훅-선택)                                          |
| 비동기 응답의 완료 순서                   | [보류 Promise 예제](references/mocking.md#응답-완료-순서-제어)                                            |
| 함수·모듈·시간 대체                       | [모킹](references/mocking.md)                                                                             |

[`concurrent`](https://vitest.dev/guide/parallelism.html#test-parallelism)는 공유 상태를 바꾸지 않는 테스트에 사용하고 콜백의 `{ expect }`로 단언합니다.
전역 모킹·가짜 시계를 변경하는 사례는 함께 실행하지 않습니다.

### 공통 준비와 도우미

검증 경계·상태 소유자·수명이 모두 같은 준비만 묶습니다. 코드 모양이 같거나 반복된다는 이유만으로 다른 경계의 준비를 합치지 않습니다.
실패 입력을 정상값으로 보정하거나 숨은 재시도·단언을 추가하지 않습니다.

| 같은 경계·소유자·수명에서 반복되는 준비 | 처리                                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 의존성·인증·클라이언트 연결             | 사례마다 독립된 상태를 만드는 팩토리                                                                               |
| 모듈 모킹·환경별 정리                   | [등록 시점과 수명을 명시한 훅](references/mocking.md#공유-모킹의-등록과-초기화); 프로젝트 전체 준비는 `setupFiles` |
| DOM·조회 캐시                           | [렌더링과 정리](references/browser-tests.md#공통-렌더링과-정리)를 함께 소유                                        |

#### 준비 코드의 배치

| 준비의 사용 범위                   | 배치                          |
| ---------------------------------- | ----------------------------- |
| 한 파일에서만 쓰는 준비            | 해당 테스트 파일 안           |
| 같은 소유 영역에서 함께 쓰는 준비  | 소유 영역의 `testing/`        |
| 독립 실행할 테스트용 자식 프로그램 | 가까운 `fixtures/<프로그램>/` |

### 단언 선택

호출자가 관찰할 반환값·오류·상태 변화·부수 효과를 검증합니다.
기대값은 요구 계약에서 직접 구합니다. 구현의 수식·내부 상수·실제 출력을 복사해 기대값을 계산하지 않습니다.

내부 연결·호출 순서 대신 적용 후 동작을 단언합니다. 외부 API의 식별자·인코딩이나 공개 설정값처럼 그 값 자체가 계약이면 직접 단언합니다.

| 항목           | 기준                                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| 원시값·동일성  | `toBe`; 객체·배열의 정확한 구조는 `toStrictEqual`                                                                     |
| 부분 계약      | 관심 있는 공개 필드만 검증할 때 `objectContaining`                                                                    |
| 오류           | 동기 `expect(() => run()).toThrow(...)`; 비동기 `await expect(run()).rejects.toThrow(...)`                            |
| 비동기 결과    | `resolves`·`rejects`·브라우저 단언과 사용자 조작은 `await`                                                            |
| 상태 변화 대기 | 완료 Promise가 있으면 직접 `await`; 상태만 조회할 수 있으면 `await expect.poll(...)`                                  |
| 호출 검증      | 외부 API에 전달할 값처럼 호출 자체가 계약일 때 `toHaveBeenCalledWith`                                                 |
| 타입 검증      | 타입·추론이 계약이면 일반 `.test.ts`·`.test.tsx`에 [expectTypeOf](references/type-tests.md)를 작성하고 실제 타입 검사 |
| 스냅샷         | 작고 안정적인 출력에 사용하며 갱신 시 차이를 직접 검토                                                                |

`expect.poll`의 재시도 콜백에는 조회만 둡니다. 쓰기·요청 시작·사용자 조작을 넣지 않습니다. 브라우저 화면은 `await expect.element(...)`로 기다립니다.

테스트의 이름·호출·단언을 사용 예제로 삼고, 주석에는 코드에서 드러나지 않는 설정 이유·실행 제약을 적습니다.

### 실패 분석·회귀 검증

가장 작은 재현 사례부터 시작하고, 그 테스트로 검증할 수 없는 경계만 실제 의존성으로 검증합니다.
원격 서비스·배포물은 [실제 환경과 배포물](references/integration-tests.md#실제-환경과-배포물)의 조건을 확인합니다.

| 확인한 원인                  | 조치                                             |
| ---------------------------- | ------------------------------------------------ |
| 요구사항 변경                | 새 계약에 맞춰 기대값 갱신                       |
| 구현 결함                    | 재현 입력으로 수정 전 실패·수정 후 통과 확인     |
| 실행 순서·시간에 따라 달라짐 | 공유 상태·대기 조건·미완료 작업 확인             |
| 단언이 결함을 잡는지 불명확  | 격리된 사본에서 관련 분기를 바꿔 실패하는지 확인 |

수정 전 재현을 확인하지 못했으면 미확인으로 보고합니다. 통과를 위한 단언 완화·임의 대기·재시도·`skip`은 추가하지 않습니다.

## 검증과 보고

[파일 포함과 검사 명령](references/type-tests.md#파일-포함과-검사-명령)으로 런타임 수집과 타입 진단 대상을 각각 확인합니다. 전체 검사에 포함된 단계는 반복하지 않습니다.
준비 공통화를 바꾸면 사례·단언·추론의 보존과 훅의 자원 회수를 확인합니다. 커버리지는 변경 분기·오류 경로의 단언과 대조하며 실행 줄 수만으로 계약 검증을 대신하지 않습니다.
실행한 명령·결과, 수정 전 재현 여부, 미실행·미확인 환경을 보고합니다.
