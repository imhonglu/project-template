# 스킬 작성·정제

로컬 스킬을 작성하며 정리한 예제·정보 배치 기준을 초안의 시작점으로 사용합니다. 정보의 역할과 작업 관계에 따라 제목·순서·파일 분리를 조정합니다.

## 정보의 역할

| 역할 | 답할 질문                             | 배치 예                                           |
| ---- | ------------------------------------- | ------------------------------------------------- |
| 선택 | 어떤 요청에 이 스킬을 쓰는가?         | `description`에 대상·수행할 작업·사용 상황        |
| 적용 | 시작 전에 무엇을 확인하는가?          | 도입부에 공통 조건, 해당 예제 앞에 환경·선행 파일 |
| 탐색 | 지금 필요한 내용은 어디에 있는가?     | 작업 선택·목차·조건별 참고 링크                   |
| 실행 | 어떻게 수행하고 어떤 결과를 얻는가?   | 대표 예제·작업 절차                               |
| 판단 | 기본 선택은 무엇이고 언제 달라지는가? | 작업별 기준·변형 예제·상세 계약                   |
| 검증 | 완료 여부를 어떻게 확인하는가?        | 절차 끝이나 결과 확인에 검사·성공 기준·보고 항목  |

스킬 선택에는 [먼저 제공되는 이름·설명](https://agentskills.io/specification#progressive-disclosure)을 사용합니다. 본문의 `사용 시점`은 설명에 없는 적용 조건이 필요할 때 둡니다. 명령의 실행 위치·필수 설정처럼 작업에 필요한 전제는 관련 내용 앞에 배치합니다.

선택한 스킬 안에서 필요한 지침을 찾도록 안내합니다. 요청마다 수행할 작업이 다르면 [작업별 탐색 예제](#작업별로-찾아-읽는-예)처럼 요청과 실행할 절을 연결합니다.

역할마다 별도 절을 만들 필요는 없습니다. 예제 하나가 실행 방법과 판단 기준을 함께 보여줄 수 있습니다. 예제로 드러나는 동작 설명은 줄이고, 입력·결과·기본값·오류·부수 효과 등 필요한 계약은 남깁니다.

## 작업에 맞게 조합하기

| 작업의 관계                       | 배치 예                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| 앞 단계의 결과가 다음 단계에 필요 | 패키지 구성: 실행 환경 → 기본 파일 → 공개 진입점 → 의존성 → 검증                            |
| 근거를 모아 내용을 구성·정제      | 문서화: 독자·근거 → 대표 사례·정보 순서 → 정제·갱신 → 검증                                  |
| 구현 중 필요한 기준을 선택        | TypeScript·테스트: [대표 예제](#예제와-판단-기준) → 모듈·타입 또는 격리·단언 기준 → 검증    |
| 요청마다 수행할 작업이 다름       | APM: [작업 선택](#작업별로-찾아-읽는-예) → 검색·패키지 관리·스킬 작성·도구 연결의 독립된 절 |
| 결과 작성과 실행 조건이 다름      | Git 커밋: [메시지 예제·작성 기준](#짧은-작업에-적용한-예) → 요청 시 커밋 생성 → 결과 확인   |

순서가 중요한 절차에는 번호를 붙이고, 독립된 작업은 같은 위계의 절로 둡니다. 완료 판단·검증은 관련 절차의 끝이나 `결과 확인`에 둡니다.

## 본문 템플릿

### 예제와 판단 기준

예제와 작업별 기준을 함께 제공할 때 사용합니다. 대괄호·스킬명·참고 파일 경로는 실제 내용으로 바꾸고, 필요한 절을 선택·조합합니다.

````markdown
---
name: task-name
description: "[대상]을 [수행할 작업]합니다. [사용 상황·대표 요청]에 사용합니다."
---

# [작업 이름]

[작업 전에 확인할 구현·환경과 공통 실행 조건]

## 기본 예제

전제: [실행 위치·필수 설정·선행 파일]

```text
[입력·실행·결과가 드러나는 대표 예제]
```

[예제에서 드러나지 않는 이유·제약]

## 작업별 기준

### [판단이 필요한 작업]

[기본 처리 방식과 선택이 달라지는 조건]

[특정 조건]이면 [상세 예제](references/task-example.md#변형)를 읽습니다.

## 결과 확인

- [결과와 실제 요구사항·구현·계약을 대조할 항목]
- [대상 환경에서 실행할 검사와 성공 판단 기준]
- [변경·검증 결과와 미실행 범위·남은 제약]
````

### 짧은 작업에 적용한 예

메시지 작성만 다루는 스킬은 예제와 작성 기준으로 본문을 완결할 수 있습니다.

````markdown
---
name: commit-message
description: Git 변경 내용을 한글 Conventional Commits 메시지로 요약합니다. 커밋 메시지 작성·정제 요청에 사용합니다.
---

# 커밋 메시지 작성

변경 내용을 확인하고 저장소의 메시지 규칙을 적용합니다.

## 메시지 예제

```text
docs(skills): 스킬 작성 기준 정리

- 작업 관계에 따른 구성 예시 추가
- 참고 문서 분리 기준 정리
```

## 작성 기준

- 제목은 `type(scope): 요약` 형식으로 작성합니다. 범위가 불필요하면 scope를 생략합니다.
- 요약은 한글 개조식으로 쓰고, 본문에는 제목만으로 전달되지 않는 변경·이유를 적습니다.

## 결과 확인

메시지와 실제 변경을 대조하고, commitlint가 구성되어 있으면 검사합니다.
````

### 작업별로 찾아 읽는 예

APM의 검색·설치·연결을 요청별로 안내하는 구조 예제입니다. 공통 실행 조건은 안내 앞에, 작업별 명령·전제·검증은 해당 절에 작성합니다.

```markdown
# 스킬·도구 관리

## 작업 선택

| 요청                  | 읽을 절                     |
| --------------------- | --------------------------- |
| 작업에 맞는 스킬 찾기 | [스킬 검색](#스킬-검색)     |
| 선택한 패키지 설치    | [패키지 설치](#패키지-설치) |
| 외부 서비스 연결      | [MCP 연결](#mcp-연결)       |

## 스킬 검색

필요한 기능으로 후보를 찾고 원본의 지원 범위·실행 조건을 비교합니다.

## 패키지 설치

설치할 패키지·배포 대상을 확인하고 선언·잠금 파일·생성물을 함께 갱신합니다.

## MCP 연결

서버의 제공 방식·인증·권한을 확인하고 대상 도구에서 연결을 검증합니다.
```

표의 각 행은 `요청: 링크` 형태의 목록으로도 표현할 수 있습니다. 주제별로 찾아 읽는 참고 문서는 [이 문서의 목차](#목차)처럼 제목을 연결합니다.

## 참고 문서 템플릿

긴 예제나 특정 환경의 절차를 본문에서 분리할 때 사용합니다. 아래는 하나의 패턴과 변형을 `references/task-example.md`에 두는 예입니다.

````markdown
# [작업·패턴 이름]

[적용할 조건과 해결할 문제]

## 기본 예제

- 실행 위치·환경: [실행 위치와 필요한 도구·설정]
- 선행 파일: [함께 제공할 구현 또는 같은 스킬 안의 예제 링크]

```text
[필요한 구현·설정과 입력·호출을 포함한 예제]
```

기대 결과: [출력·상태 변화·완료 판단]

[예제에서 드러나지 않는 제약과 해당 근거]

## 변형

[기본 예제와 선택이 달라지는 조건]

```text
[달라지는 부분의 예제와 적용 위치]
```

[변경된 결과·주의점과 검증 방법]
````

| 담을 내용               | 구성 예                                                         |
| ----------------------- | --------------------------------------------------------------- |
| 같은 패턴의 조건별 차이 | 기본 예제 → 선택이 달라지는 조건·변형                           |
| 독립된 패턴 모음        | 입력 검증·상태 표현처럼 각각 완결된 예제를 같은 위계에 배치     |
| 문서 작성 예            | README·탐색 안내의 구조를 코드 블록으로 제시하고 작성 조건 보완 |

실행 예제·타입 검사 전용 예제·구조 예제를 구분합니다. 함께 필요한 파일은 제공하거나 연결하고, 발췌한 예제는 적용 위치와 보완할 부분을 밝힙니다. 본문에서는 읽을 조건과 해당 절을 연결하며 파일명·API 이름을 예제와 맞춥니다.

## 실제 사용으로 개선하기

대표 요청에 적용한 결과와 사용자의 수정을 근거로 다듬습니다. 새 정보는 기존 문장·절에 통합하고, 필요한 기본값·지원 범위·실패 조건은 보존합니다.

| 사용 중 확인한 문제                                 | 반영 예                                                          |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| 필요한 요청에서 스킬 선택을 놓침                    | description에 빠진 작업·상황을 보완; 실제로 혼동되는 경계만 명시 |
| 예제 실행에 필요한 정보가 뒤늦게 등장               | 실행 위치·설정·선행 파일을 예제 앞으로 이동                      |
| 관련 예제를 찾지 못하거나 여러 문서를 반복해서 읽음 | 조건별 링크와 제목 앵커를 정리하고 상세 설명을 한 곳에 모음      |
| 선택지·예외가 쌓여 기본 동작이 불분명함             | 기본 처리 방식을 먼저 제시하고 판단이 바뀌는 조건별로 재구성     |

반복해서 유용한 구성은 이 템플릿에도 반영합니다. 특정 환경의 문제는 해당 예제의 조건으로 다루고, 기존 스킬은 같은 문제가 확인된 부분부터 개선합니다. 새 구성이 더 명확해지면 절·예제·참고 파일을 합치거나 나눌 수 있습니다.

역할을 다른 스킬로 옮기면 상세 기준·예제의 정본과 양쪽 설명을 함께 갱신합니다. 각 스킬에는 작업 완료에 필요한 기준을 남깁니다. 예를 들어 README 작성법을 분리해도 패키지 구성에는 공개 경로·실행 조건·개발 명령을 확인하는 기준이 필요합니다.

## 근거·검증

- 공식 작성 가이드와 유사한 공개 스킬의 본문·참고 파일을 비교해 적용할 패턴과 이유를 정합니다. 근거는 해당 내용 가까이에 연결합니다.
- 대표 요청에서 필요한 절·참고 예제를 선택하고 작업을 완료할 수 있는지 확인합니다. 공통 제목의 유무보다 정보의 연결과 빠진 전제를 살핍니다.
- 이름·설명 메타데이터와 상대 링크를 검사합니다. 예제의 목적에 맞게 구조·타입·실행 결과를 검증하고, 명령 옵션은 도구 도움말로 확인합니다.
