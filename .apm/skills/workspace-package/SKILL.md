# 워크스페이스 패키지

기존 워크스페이스의 패키지 검색 범위·이름·실행 환경·검사 명령을 먼저 확인합니다.
아래 예제는 pnpm·TypeScript·Vitest를 사용하는 비공개 ESM 모노레포 기준입니다.

프레임워크별 설정은 설치 버전의 공식 문서와 대조합니다. Vite를 사용하면 [공식 색인](https://vite.dev/llms.txt)에서 해당 기능을 찾을 수 있습니다.

## 작업 절차

패키지의 소비자와 공개 경로를 확인하고 다음 순서로 적용합니다.

### 1. 패키지 경계

| 상황                                           | 배치                             |
| ---------------------------------------------- | -------------------------------- |
| 기존 기능과 함께 변경하는 구현·검증 도구       | 소유 패키지 안의 관심사 디렉터리 |
| 같은 패키지에서 소비 목적·실행 환경이 다른 API | 배럴과 `exports` 하위 경로       |
| 독립적인 소비자·의존성·배포 수명               | 별도 워크스페이스 패키지         |

파일 이동·공통화 전에는 [로직 소유권과 호환성](references/ownership.md)에서 계약·변경 이유·자원 수명을 비교합니다.

### 2. 실행 환경과 파일 구성

[패키지 구성 예제](references/package-configuration.md)를 읽고 필요한 설정만 적용합니다.

- `tsconfig.json`은 공통 설정을 상속해 소스·테스트·도구 설정을 검사합니다. 환경을 나누거나 합치면 [타입 검사 범위](references/package-configuration.md#타입-검사-범위)를 확인합니다.
- `exports`·스크립트·타입 선언 경로는 실제 소비할 소스 또는 빌드 산출물에 맞춥니다.
- 공통 검사는 루트에서, 환경별 빌드·테스트는 패키지에서 관리합니다. 독립 배포는 [빌드와 릴리스 소유권](references/package-configuration.md#빌드와-릴리스-소유권)을 따릅니다.

### 3. 공개 API와 실행 진입점

[진입점 예제](references/entry-points.md)를 읽습니다.

| 파일·경로                               | 역할                                           |
| --------------------------------------- | ---------------------------------------------- |
| `src/index.ts`                          | 소비자에게 제공할 모듈의 배럴                  |
| `src/main.ts` 또는 `<프로그램>/main.ts` | 인수·신호·표준 출력·종료 코드 연결             |
| `src/testing/index.ts`                  | 소비자가 사용할 검증 도구가 있을 때의 배럴     |
| `src/node.ts`                           | 공통 API와 Node.js 실행 API를 분리할 때의 배럴 |

다른 패키지는 `exports`로 공개한 경로를, 내부 구현은 자신의 배럴을 거치지 않고 소유 파일을 참조합니다.

단일 공개 진입점으로 시작하고 소비 목적·환경·전용 의존성이 달라질 때 하위 경로를 추가합니다.
같은 API의 구현만 환경별로 다르면 conditional exports를 검토합니다.

미사용 코드 분석 도구에는 공개 경로와 실행 진입점 규칙을 등록합니다.

### 4. 부수 효과

`sideEffects`는 import 시 필요한 부수 효과를 번들러에 알립니다. 내보낸 함수를 호출할 때의 효과는 제외합니다.

| import 시 필요한 부수 효과               | 선언                |
| ---------------------------------------- | ------------------- |
| 없음                                     | `false`             |
| CSS·폴리필·전역 등록 등 일부 파일에 있음 | 해당 파일·glob 배열 |
| 확인하지 못함                            | 생략                |

초기화 경로를 공개하면 [부수 효과를 보존하는 경로](references/entry-points.md#부수-효과를-보존하는-경로)를 확인합니다.
소비자의 프로덕션 빌드에서 미사용 모듈 제거와 필요한 초기화 보존을 확인합니다. `sideEffects`는 Node.js의 모듈 로드를 제어하지 않습니다.

### 5. 테스트와 의존성

제품 테스트는 구현 옆에, 재사용 도우미는 소유 영역의 `testing/`에 둡니다. 자식 프로그램은 가까운 픽스처 디렉터리에 둡니다.
외부 소비자가 사용하는 검증 API·도우미만 공개하고 내부 테스트 준비는 배럴에서 제외합니다.
독립적인 검증 프로그램과 제품 기능의 테스트 도우미는 [소유권 기준](references/ownership.md#디렉터리와-의존-방향)으로 구분합니다.

- 루트 테스트 설정이 패키지의 테스트 프로젝트를 수집하는지 확인합니다.
- pnpm 내부 의존성은 `workspace:*`, catalog로 관리하는 공유 버전은 `catalog:`로 참조합니다.
- 선언을 변경한 뒤 설치 도구로 잠금 파일을 갱신합니다.

```sh
pnpm install
```

## 결과 확인

- 소비자의 공개 경로 import·타입 검사·빌드와 실행 명령을 확인합니다. 라이브러리 import만으로 서비스·검증 명령을 시작하거나 프로세스 종료 정책을 변경하지 않습니다.
- README의 경로·명령·실행 조건과 실제 설정을 대조합니다.
- 패키지 분리·의존성 이동 후에도 전이 의존성의 변경이 빌드·검증 캐시를 갱신하는지 확인합니다.
- 저장소의 전체 검사 명령을 실행하고, 여기에 포함되지 않은 관련 빌드·소비자 검사는 별도로 실행합니다.
- 변경 내용·검증 결과·남은 제약을 보고하고, 기존 실패와 이번 변경으로 발생한 실패를 구분합니다.
