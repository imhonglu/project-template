# 명료한 표현과 편집 예제

한국어 표현·제약·템플릿·구조를 다듬을 때 읽습니다. 예제는 자체 작성했으며 외부 지침의 예문·표를 옮기지 않았습니다.

## 원래 형식에서 표현부터 다듬기

제목·강조·목록·작성자용 HTML 주석의 역할을 살립니다. 본문은 기존 문체를 따르고, 힌트·제약에는 자연스러운 구·명사형을 씁니다.

**원문**

```markdown
_<!-- 이 코드를 잘 모르는 독자도 이해할 수 있도록 변경 내용을 쉬운 말로 120자 이내로 요약합니다. -->_
```

**편집**

```markdown
_<!-- 이 코드를 잘 모르는 독자도 이해할 수 있도록 변경 내용을 쉬운 말로 요약. 길이 <= 120자 -->_
```

다음 PR 템플릿의 형식·길이 제한은 이 예제의 조건입니다. `pnpm check`가 정의된 저장소를 가정합니다.

```markdown
#### 배경

<!-- 변경이 필요한 이유. 길이 <= 240자 -->

#### 한 줄 요약

_<!-- 이 코드를 잘 모르는 독자도 이해할 수 있도록 변경 내용을 쉬운 말로 요약. 길이 <= 120자 -->_

#### 변경 사항

- <!-- 변경 사항을 항목별로 정리 -->
- <!-- 핵심 내용 위주 -->
- <!-- 각 항목 <= 120자 -->

#### 검토한 대안

- <!-- 검토한 대안과 채택하지 않은 이유 -->

#### 테스트 계획

- [ ] `pnpm check`
- [ ] <!-- 변경 사항에 필요한 추가 검증 항목 -->
```

## 용어와 같은 역할의 형식 맞추기

같은 개념의 이름과 같은 역할의 제목·표 항목을 맞춥니다. 다른 개념을 합치거나 모든 문장 어미를 통일하지는 않습니다.

| 대상             | 편집 예                                                       |
| ---------------- | ------------------------------------------------------------- |
| 같은 개념의 이름 | `호출 이력`·`호출 기록` → `호출 기록`                         |
| 같은 위계의 제목 | `의존성 설치`·`설정을 적용합니다` → `의존성 설치`·`설정 적용` |

## 짧게 써도 경계와 책임 남기기

| 원문                                                          | 편집                                      | 보존할 의미                      |
| ------------------------------------------------------------- | ----------------------------------------- | -------------------------------- |
| 파일 크기는 10 MB 미만이어야 합니다.                          | 파일 크기 < 10 MB                         | 단위 유지, 10 MB 제외            |
| 대기 시간은 0밀리초 이상 5000밀리초 이하입니다.               | 0 ms <= 대기 시간 <= 5000 ms              | 같은 단위, 양끝 포함             |
| 운영자가 승인한 뒤 삭제합니다. 보존 대상은 삭제하지 않습니다. | 운영자 승인 후 삭제. 보존 대상 삭제 금지. | 승인 주체·순서, 예외 대상의 금지 |
| 명령을 아직 실행하지 않았습니다.                              | 미실행                                    | 실행 여부이지 사실의 진위가 아님 |
| 반환값을 수정할 수 있는지는 확인하지 못했습니다.              | 반환값 수정 허용 여부 미확인              | 허용·금지 모두 미확정            |

불명확한 표현은 근거를 확인해 구체화하고, 확인하지 못하면 미확인으로 남깁니다. `최대 크기 근처에서 실패`만으로 `<`와 `<=`를 정하지 않습니다.
`적절히 처리합니다`는 실패 시 임시 파일 삭제를 확인했다면 `실패하면 임시 파일을 삭제합니다`로 씁니다.

쓰기 완료 시점과 종료 책임을 확인한 경우:

- 원문: 직접 연 파일을 닫습니다. 풀의 재사용·서비스 재시작·싱글턴의 테스트 격리도 검토합니다.
- 편집: 쓰기 완료를 기다린 뒤 직접 연 파일을 닫습니다. 주입받은 파일의 종료 책임은 호출자에게 남습니다.

완료 시점·소유권은 남기고, 이 API 설명의 범위를 벗어난 운영 주제는 덜어냈습니다.

## 구조는 정보의 관계에 따라 선택하기

### 따라 할 순서가 있으면 번호 목록

아래 명령이 정의된 프로젝트의 절차 예제입니다. 설치·자동 수정은 파일을 바꿀 수 있습니다.

**짧은 안내**

> `pnpm install`로 설치하고 `pnpm fix`로 수정한 뒤 `pnpm check`로 검사합니다.

**단계별로 따라 할 때**

```markdown
저장소 루트에서 실행합니다.

1. `pnpm install`로 의존성을 설치합니다.
2. `pnpm fix`로 린트·포맷을 자동 수정합니다.
3. `pnpm check`로 검사합니다.
```

단계를 찾아 실행할 필요가 없다면 짧은 안내로 충분합니다.

### 목적별로 고르면 표

자동 수정과 파일 수정 없는 검사를 고르는 예제입니다.

```markdown
| 목적                     | 명령         |
| ------------------------ | ------------ |
| 린트·포맷 자동 수정      | `pnpm fix`   |
| 파일 수정 없이 전체 검사 | `pnpm check` |
```

선택지가 적으면 “수정하려면 `pnpm fix`를, 파일 수정 없이 검사하려면 `pnpm check`를 실행합니다”로 충분합니다.
설치·검사·문제 해결처럼 독립된 주제는 같은 위계의 제목으로 나눕니다.

## 중복을 줄여도 사용 조건은 남기기

제목·타입·예제에서 이미 알 수 있는 정보는 덜어냅니다.

```ts
export * from "./parse-input.ts";
export type * from "./transport.ts";
```

모듈 구현을 생략한 재수출 예제입니다. 옆 설명은 `공개 배럴은 소비자용 모듈을 재수출합니다`로 충분합니다. `export *`와 `export type *`의 차이는 코드에 드러납니다.
코드에 없는 지원 환경·오류·부수 효과는 남깁니다. 예를 들어 `check`가 첫 실패에서 중단한다면 실행 위치·성공 기준과 함께 `첫 실패 이후의 검사는 실행되지 않습니다`를 설명합니다.
`작업 목적에 맞는 명령을 사용합니다`처럼 정보가 없는 일반론은 삭제합니다.

## Markdown 외부 링크

자료 하나는 설명 가까이에 두고, 링크 이름에 확인할 내용을 씁니다.

```markdown
참고: [pnpm 패키지 선택](https://pnpm.io/filtering)

대상 패키지는 [pnpm 필터](https://pnpm.io/filtering)로 선택합니다.
```

문맥에 맞는 방식 하나를 고릅니다. 여러 자료는 참고 목록으로, 다른 주제는 소제목으로 묶습니다. 항목마다 `참고:`를 반복하지 않습니다.

```markdown
## 참고

### 실행 명령

- [pnpm 패키지 선택](https://pnpm.io/filtering)
- [Vitest 프로젝트별 실행](https://vitest.dev/guide/projects.html#running-tests)

### 문서 구성

- [GitHub README 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)
```

## 출처와 적용 범위

### 한국어 기술 문서의 독자 중심 편집

- [ISO 24495-1:2023 공개 개요](https://www.iso.org/standard/78907.html): 언어에 한정되지 않는 쉬운 언어 원칙으로 기술 문서에도 적용할 수 있습니다. 유료 전문은 검토하지 않았습니다.
- [국제 쉬운 언어 연맹의 공개 해설](https://www.iplfederation.org/wp-content/uploads/2024/06/Plain-language-certification-for-organizations_A-Consultation-Paper-1-1.pdf): 관련성·검색 용이성·이해 가능성·사용 가능성을 설명합니다. 이 스킬은 독자의 작업, 정보 위치, 표현, 적용 경로를 확인하는 데 활용합니다. 의미 보존은 별도로 대조하며, 표준 적합성·조직 인증·실제 독자의 성공을 판정하지 않습니다.
- [국립국어원 쉬운 공문서 쓰기 길잡이(2022)](https://www.korean.go.kr/front/etcData/etcDataView.do?etc_seq=700): 독자 관점과 정확한 표현을 참고합니다. 공문서용 안내이지 한국어 통제 언어 규격은 아닙니다. 공공누리 제3유형(출처표시·변경금지) 자료이므로 원문은 링크로 제공합니다.

### 별도 요청이 있을 때만 적용 범위 확인

- 제품 사용 설명서: [KS C IEC/IEEE 82079-1 공개 목록](https://www.kssn.net/search/stddetail.do?itemNo=K001010145434)은 제품 사용 정보의 작성·구성을 다룹니다. 목록·범위만 참고했으며, 전문 없이 조항별 적합성을 주장하지 않습니다. 한국어 어휘·문법이나 모든 README의 작성 규칙으로 쓰지 않습니다.
- 영어 통제 언어 검토: [ASD-STE100 소개](https://www.asd-ste100.org/about_STE.html)와 [공식 Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf)를 참고하고, 요청한 판본의 전체 규칙·사전으로 검토합니다. 영어용이므로 한국어에 단어 수·사전 제한을 적용하지 않습니다. [배포·사용 조건](https://www.asd-ste100.org/STE_downloads.html)을 확인하고 원문 규칙·사전을 복제하지 않습니다.
