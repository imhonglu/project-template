# 문서 작성·정비

독자가 할 일에 맞춰 읽는 순서를 정하고, 사용법은 대표 예제를 중심으로 설명합니다.
기존 언어·용어와 사실·사용 조건은 보존합니다.

## 작업 절차

### 1. 독자·근거 확인

독자가 문서를 읽고 할 일과 확인할 근거를 정합니다. 결과를 좌우하는 정보가 부족하면 질문합니다.

| 설명할 내용         | 확인할 근거                     |
| ------------------- | ------------------------------- |
| 사용법·지원 범위    | 공개 API·명령·설정·테스트       |
| API 주석·사용 예    | 선언·구현·호출부·동작 테스트    |
| 설계·선택 이유      | 요구사항·논의·현재 구현         |
| 작업 지침·작성 규칙 | 적용할 작업·실제 절차·기존 관례 |

설계안은 확인한 사실·가정·제안하는 계약을 구분합니다. 결정 기록에는 선택 근거와 다시 검토할 조건을 남깁니다.
작업 지침은 적용 사례·반례로 검토하고, API의 보장과 프로젝트 관례를 구분합니다.

### 2. 대표 예제·정보 순서 설계

| 독자가 할 일        | 읽는 순서                         | 참고 예제                                    |
| ------------------- | --------------------------------- | -------------------------------------------- |
| 프로젝트 시작       | 소개 → 최초 실행 → 관련 안내      | [루트 README](references/readme.md#루트)     |
| 특정 기능 사용      | 소개 → 사용법 → 개발              | [패키지 README](references/readme.md#패키지) |
| 절차·작성 기준 적용 | 적용 조건 → 예제 → 판단 기준·검증 | [사용 안내](#사용-안내-예제)                 |
| 설계 제안·선택 검토 | 문제·제약 → 제안·근거 → 대안·검증 | [설계안](#설계안-예제)                       |

- 실행 안내에는 위치·필수 설정·선행 파일을 적습니다.
- 실행 예제는 필요한 구현·설정을 제공하거나 연결합니다. 구조 설명용 예제·발췌 코드는 적용 위치와 보완할 부분을 표시합니다.
- 사용 안내에는 실제 공개 경로·명령을, 설계안에는 제안할 경로·계약을 적습니다.
- 실행 예제가 파일을 변경하거나 외부 요청을 보내면 그 효과를 밝히고 비밀값은 제외합니다.

골라 읽을 내용이 많으면 주제별 목차나 상황별 선택표로 해당 절을 연결합니다.

#### 사용 안내 예제

전제: 루트 `test` 스크립트가 Vitest를 실행하고 `@project-template/example` 프로젝트가 등록된 구성입니다.

````markdown
# 특정 패키지 테스트하기

워크스페이스 설치를 마친 뒤 저장소 루트에서 실행합니다.

```sh
pnpm test --project @project-template/example
```

테스트가 실행되고 명령이 종료 코드 0으로 끝나면 성공입니다.

`No projects were found`가 나오면 루트의 프로젝트 검색 경로와 패키지의 테스트 설정을 확인합니다.
````

#### 설계안 예제

선택을 바꾸는 조건과 확인 방법을 남깁니다. 짧은 결정은 한 문단으로 묶습니다.

```markdown
## 제안과 근거

파일 내보내기에 작업 ID를 반환하고 결과를 조회하는 방식을 제안합니다.
큰 파일의 처리 시간이 HTTP 요청 제한을 넘길 수 있다는 가정입니다.

## 대안과 확인

지원할 최대 파일 크기·동시 요청 수에서 처리 시간을 측정합니다.
응답 시간 목표를 충족하면 동기 응답을 선택합니다.
```

### 3. 설명 통합·구조 정제

문장을 빼도 독자의 행동·판단이 같으면 삭제합니다. 선택 근거나 실행·승인 조건, 계약의 보장 범위가 달라지면 남깁니다.
문단은 한 주제로 묶고, 원본 줄바꿈은 문장·의미 단위를 따릅니다.

#### 제목·예제·주석과 겹치는 설명 삭제

제목·타입·예제에서 같은 정보와 적용 범위를 알 수 있으면 중복 설명을 덜어냅니다.

```ts
export * from "./parse-input.ts";
export type * from "./transport.ts";
```

**Avoid**

> 공개 배럴은 소비자용 모듈을 `export *`로, 타입만 제공할 때는 `export type *`로 재수출합니다.

**Good**

> 공개 배럴은 소비자용 모듈을 재수출합니다.

#### 추상적인 안내를 구체화하고 일반론 삭제

소개는 독자가 할 일로 구체화합니다. 행동·선택 근거를 더하지 않는 권고는 삭제합니다.

**Avoid**

> 개발 작업을 도와주는 안내입니다. 작업 목적에 맞는 명령을 사용합니다.

**Good**

> 의존성 설치와 코드 자동 수정·검사 절차를 안내합니다.

#### 실행 예제를 보완하고 필요한 조건 보존

명령·입력·결과는 예제로 보여주고, 예제에서 드러나지 않는 기본값·범위·실패·부수 효과·승인 조건은 남깁니다.

전제: `check`는 전체 검사를 순서대로 실행하고 첫 실패에서 중단합니다.

**Avoid — 실행 방법 누락**

> 프로젝트를 검사합니다. 검사가 실패하면 이후 검사는 실행되지 않습니다.

**Good**

````markdown
저장소 루트에서 실행합니다.

```sh
pnpm check
```

종료 코드 0이면 성공입니다.
첫 실패에서 중단하므로 이후 검사는 실행되지 않습니다.
````

#### 순서·선택·주제를 구조로 구분

##### 순서가 있는 작업은 번호 목록

**Good — 짧은 안내**

> `pnpm install`로 설치하고 `pnpm fix`로 수정한 뒤 `pnpm check`로 검사합니다.

**Better — 각 단계를 따라 실행할 때**

```markdown
1. `pnpm install`로 의존성을 설치합니다.
2. `pnpm fix`로 린트·포맷을 자동 수정합니다.
3. `pnpm check`로 검사합니다.
```

##### 조건에 따른 선택은 표

**Good — 짧은 안내**

> 수정하려면 `pnpm fix`를, 파일 수정 없이 검사하려면 `pnpm check`를 실행합니다.

**Better — 목적별 명령을 찾아볼 때**

```markdown
| 목적                     | 명령         |
| ------------------------ | ------------ |
| 린트·포맷 자동 수정      | `pnpm fix`   |
| 파일 수정 없이 전체 검사 | `pnpm check` |
```

##### 독립된 주제는 같은 위계의 헤딩

```markdown
## 설치

필요한 도구와 의존성 설치 명령

## 검사

검사 명령과 성공 기준

## 문제 해결

실패 증상별 원인과 해결 방법
```

#### 현재 작업에서 판단하지 않는 조건 나열 삭제

파일 API의 종료 책임을 설명하는 경우입니다.

**Avoid**

> 직접 연 파일을 닫습니다. 풀의 재사용·서비스 재시작·싱글턴의 테스트 격리도 검토합니다.

**Good**

> 쓰기 완료를 기다린 뒤 직접 연 파일을 닫습니다. 주입받은 파일의 종료 책임은 호출자에게 남습니다.

#### 여러 안내에 반복한 규칙은 정본으로 통합

규칙은 정본 한 곳에서 관리하고, 다른 안내에는 링크나 적용 예를 둡니다.

**Avoid**

> 스킬 작성 가이드와 문서화 가이드 양쪽에 Markdown 외부 링크 표기를 설명합니다.

**Good**

- 문서화 가이드: Markdown 외부 링크 표기
- 스킬 작성 가이드: 참고 파일을 읽을 조건과 링크 적용 예

버전·설정 전체는 관리 파일로 연결합니다. 사용에 필요한 기본값·제약은 원본과 대조해 설명합니다.

#### 독립된 목적이 없는 절·참고 문서 통합

본문에 합친 뒤 별도 절차·예제·판단 기준이 남지 않으면 절·파일을 삭제하고 참조를 갱신합니다.

**Avoid**

> 본문과 `navigation.md`에서 목차·작업 선택표의 기본 안내를 반복합니다.

**Good**

> 목차·작업 선택표 안내는 본문의 정보 순서 설계 절에 모으고 `navigation.md`를 삭제합니다.

#### Markdown 외부 링크

외부 자료는 관련 설명 가까이에 두고, 링크 이름에 확인할 내용을 적습니다.
단일 자료는 `참고:`·`- 참고:` 또는 문장 안에 연결합니다.

```markdown
참고: [pnpm 패키지 선택](https://pnpm.io/filtering)

대상 패키지는 [pnpm 필터](https://pnpm.io/filtering)로 선택합니다.
```

여러 자료는 참고 절이나 목록으로 나누고, 주제가 다르면 소제목으로 묶습니다.
제목·목록이 역할을 드러내면 항목마다 `참고:`를 반복하지 않습니다.

```markdown
## 참고

### 실행 명령

- [pnpm 패키지 선택](https://pnpm.io/filtering)
- [Vitest 프로젝트별 실행](https://vitest.dev/guide/projects.html#running-tests)

### 문서 구성

- [GitHub README 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)
```

#### API 설명의 위치

| 설명할 내용                                          | 위치                                      |
| ---------------------------------------------------- | ----------------------------------------- |
| 입력·기본값·결과·오류·부수 효과·소유권, 대표 사용 예 | 해당 선언의 문서 주석                     |
| 설치·실행·기능을 조합하는 절차                       | 사용 안내에서 설명하고 상세 계약으로 연결 |
| 알고리즘·우회 처리 등 구현 선택의 이유               | 해당 구현 옆 주석                         |

[API 계약 비교 예제](references/api-contracts.md)처럼 이름·타입에서 드러나지 않는 사용 조건을 적습니다.
태그·링크·코드 예제는 해당 언어의 문서 주석 문법을 따릅니다.

### 4. 변경과 문서 연결

변경된 이름·용어·규칙으로 관련 설명과 예제를 찾아 함께 갱신합니다.

| 변경                | 확인할 내용                             |
| ------------------- | --------------------------------------- |
| 공개 진입점·이름    | import 경로·호출 예제·링크              |
| 명령·설정           | 준비 조건·필수 옵션·생략 시 동작        |
| 동작·지원 범위      | 기대 결과·제약·문제 해결·이전 안내      |
| 작업 지침·작성 규칙 | 소개·적용 조건·절차·예제·참고 자료 연결 |

완료한 작업의 기록을 정리할 때는 현재 독자가 다시 찾을 정보를 남깁니다.

| 정보                              | 유지할 위치                              |
| --------------------------------- | ---------------------------------------- |
| 현재 동작·제약·선택 이유          | 사용 안내·API 계약·설계의 해당 절        |
| 미완료 작업·외부 준비 조건        | 계획과 완료 기준                         |
| 재현·비교·인수 판단에 필요한 결과 | 리비전·환경·미확인 범위를 담은 검증 기록 |

보존 의무가 없는 반복 요약·중간 기록은 정본에 반영한 뒤 제거하고 링크를 갱신합니다.
장기 참조 근거는 영구적으로 접근할 수 있는 위치에 둡니다.

## 결과 확인

### 내용·구조

- 독자의 주제·요청에서 필요한 절로 이동해 적용 조건·예제·결과 또는 판단 근거를 찾을 수 있는지 확인합니다.
- 설계안의 제안·대안을 같은 요구사항으로 비교하고, 가정의 확인 방법과 결정 상태를 구분합니다.
- 삭제·재구성 뒤에도 실행 조건·계약·실패 처리가 드러나는지 확인합니다.
- 자동 편집·포맷 뒤에도 원본 diff에서 문단·태그·코드 블록의 경계를 확인합니다.
- API 주석의 계약을 구현·테스트와 대조합니다.
- 링크·앵커·공개 경로와 포맷·철자를 검사합니다. IDE·렌더링 도구가 있으면 태그·링크·예제 표시도 확인합니다.

### 예제 검증

- 작성·수정한 예제는 목적에 맞게 검증합니다. 구조·계약 제안은 전제와 대조하고, 실행·타입 검사 예제는 코드 블록도 검사합니다.
- 외부 서비스·데이터 변경이 필요한 예제는 격리된 환경과 요청 범위에서 검증합니다.

변경·검증 결과와 미실행 예제·확인되지 않은 사실을 보고합니다.
