# 문서 작성·정제

독자가 필요한 정보를 찾아 이해하고, 행동하거나 판단할 수 있도록 씁니다. 쓸모 있는 구조와 기술적 의미는 보존합니다.
아래 절차는 ISO 24495-1의 네 원칙을 문서 작업에 적용한 것입니다. [출처와 적용 범위](references/clear-writing.md#출처와-적용-범위)를 참고합니다.

## 작업 절차

### 1. 독자의 작업과 근거 정하기

독자와 할 일, 바꿀 문서의 범위를 정합니다. 제공된 자료와 원본을 먼저 읽고, 부족한 필수 정보만 질문합니다.

| 설명할 내용         | 대조할 근거                     |
| ------------------- | ------------------------------- |
| 사용법·지원 범위    | 공개 API·명령·설정·테스트       |
| API 주석·사용 예제  | 선언·구현·호출부·동작 테스트    |
| 설계·선택 이유      | 요구사항·논의·현재 구현         |
| 작업 지침·작성 규칙 | 적용할 작업·실제 절차·기존 관례 |

사실·가정·제안을 구분하고, 근거보다 넓은 보장을 쓰지 않습니다. 설계·결정 기록에는 선택 근거와 재검토 조건을 남깁니다. API 보장과 프로젝트 관례도 구분합니다.
근거가 충돌하면 의도한 계약을 확인하고 미해결 차이를 밝힙니다. 문서 작업에서 구현까지 고치지 않으며, 표현만 다듬을 때는 기술 결정을 유지합니다.

### 2. 필요한 위치에 정보 놓기

제목·목록·강조·작성자용 HTML 주석이 제 역할을 하면 유지합니다. 구조는 탐색과 사용이 나아질 때 바꿉니다.
작업에 맞는 참고 문서를 읽습니다.

| 작업                  | 정보 순서·위치                                   | 참고                                                |
| --------------------- | ------------------------------------------------ | --------------------------------------------------- |
| 프로젝트 시작 안내    | 소개 → 최초 실행 → 관련 안내                     | [루트 README](references/readme.md#루트)            |
| 패키지·기능 사용 안내 | 소개 → 사용법 → 개발·제약                        | [패키지 README](references/readme.md#패키지)        |
| API 주석·계약         | 소유 선언에 계약, 사용 안내에 조합 절차          | [API 계약과 주석 위치](references/api-contracts.md) |
| 절차·작성 기준        | 적용 조건 → 예제 → 결과·판단 기준                | [사용 안내 예제](#사용-안내-예제)                   |
| 설계 제안·결정 기록   | 문제·제약 → 제안·근거 → 대안·확인 방법·결정 상태 | [설계안 예제](#설계안-예제)                         |

실행 전에 작업 디렉터리와 필수 설정·파일을 안내합니다. 실제 공개 경로·명령을 쓰고 필요한 구현·설정으로 연결합니다.
파일 변경·외부 요청 등 실행 효과와 실패 대응을 설명합니다. 비밀값은 넣지 않습니다.
템플릿·제안·발췌·모의 응답은 목적과 생략한 구현을 밝혀 실행 예제와 구분합니다.
골라 읽을 내용이 많으면 목차나 선택표로 연결합니다.

#### 사용 안내 예제

루트 `test`가 Vitest를 실행하고 `@project-template/example` 프로젝트가 등록된 경우의 안내 예제입니다.

````markdown
# 특정 패키지 테스트하기

워크스페이스 설치를 마친 뒤 저장소 루트에서 실행합니다.

```sh
pnpm test --project @project-template/example
```

테스트가 실행되고 명령이 종료 코드 0으로 끝나면 성공입니다.
`No projects were found`가 나오면 루트의 프로젝트 검색 경로와 패키지의 테스트 설정을 확인합니다.
````

#### 설계안 예제

미결정 계약의 제안 예제입니다. 결정 기록이라면 선택한 대안과 근거, 재검토 조건을 적습니다.

```markdown
## 제안과 근거

파일 내보내기에 작업 ID를 반환하고 결과를 조회하는 방식을 제안합니다.
큰 파일의 처리 시간이 HTTP 요청 제한을 넘길 수 있다는 가정입니다.

## 대안과 확인

지원할 최대 파일 크기·동시 요청 수에서 동기 응답과 작업 ID 방식의 처리 시간을 비교합니다.
동기 응답이 응답 시간 목표를 충족하면 동기 응답을 선택합니다.
측정 전이므로 방식은 미결정입니다.
```

### 3. 이해하기 쉽게 다듬고 의미 보존하기

같은 개념은 같은 용어로 쓰고, 다른 상태·책임은 구분합니다. 식별자·경로·명령·코드 리터럴은 실제 표기를 유지합니다.
불명확한 주체·동작·대상·조건은 근거로 구체화합니다. 문장을 빼도 독자의 행동·판단이 같으면 덜어냅니다.
타입·예제를 반복하는 설명은 빼고, 드러나지 않는 기본값·범위·실패·부수 효과·승인·소유권은 남깁니다.

글의 역할과 기존 문체를 따릅니다. 같은 역할의 제목·표 항목은 형식을 맞추되 문장 어미까지 통일하지 않습니다. 힌트·제약·목록에는 자연스러운 구·명사형도 씁니다.
수치는 단위·예외·경계값 포함 여부를 보존해 `<=` 등으로 쓸 수 있습니다.
문장·목록·줄바꿈은 의미 관계에 따라 고릅니다. 조건을 `·`로 몰아넣거나 고정된 길이·형식을 강제하지 않습니다.

한국어 표현·제약·템플릿·구조를 다듬을 때는 [명료한 표현과 편집 예제](references/clear-writing.md)를 읽습니다.

### 4. 독자의 작업을 따라 확인하고 연결 갱신하기

독자의 작업 하나를 골라 조건·예제·결과나 판단 근거까지 따라갑니다. 작업 지침은 적용 사례와 반례로 확인합니다. 설계안은 같은 요구사항에서 대안을 비교할 수 있는지 봅니다.

| 확인 대상   | 볼 내용                                                                    |
| ----------- | -------------------------------------------------------------------------- |
| 필요한 정보 | 작업에 필요한 조건·근거가 있고 무관한 일반론은 없는가?                     |
| 찾을 위치   | 제목·목차로 찾을 수 있고 링크·앵커·공개 경로가 맞는가?                     |
| 이해 단서   | 필요한 용어·약어가 설명되고 주체·동작·조건이 명확한가?                     |
| 의미 보존   | 계약·금지·승인·예외·수치 범위가 같고 용어·Markdown·주석 경계가 유지되는가? |
| 적용 가능성 | 준비부터 결과·실패 대응까지 이어지고 제안·템플릿·실행 예제가 구별되는가?   |

이름·명령의 변경을 관련 설명과 예제에 반영합니다. 이름이 그대로여도 동작·지원 범위·설정·규칙이 바뀌면 갱신합니다. 준비 조건·기대 결과·제약·문제 해결·이전 안내도 살핍니다.
설명 정본은 한 곳에 두고 다른 곳에서는 링크나 적용 예로 연결합니다. 역할이 겹친 절·참고 문서는 통합합니다.
버전·설정 전체는 관리 파일로 연결하고, 사용에 필요한 기본값·제약은 원본과 대조해 남깁니다.
외부 출처는 설명 가까이에 내용이 드러나는 이름으로 연결합니다. 여러 자료는 주제별로 묶고 접근 제한은 밝힙니다. [Markdown 외부 링크 예제](references/clear-writing.md#markdown-외부-링크)를 참고합니다.

작업 기록도 정리한다면 현재 동작·제약·선택 이유는 해당 사용 안내·API 계약·설계에 반영합니다. 미완료 작업·외부 준비 조건은 계획에, 재현·인수 근거는 리비전·환경·미확인 범위와 함께 검증 기록에 둡니다.
중간 기록은 정본 반영과 삭제 허용 범위를 확인한 뒤 제거합니다.

예제는 요청 범위·환경·실행 효과에 맞춰 검증합니다. 실행 예제는 관련 실행·타입 검사로, 타입 전용 예제는 타입 검사로, 구조·계약 제안은 명시한 전제와 대조합니다.
외부 서비스·데이터를 바꾸는 실행은 허용된 격리 환경에서만 합니다. 표현 수정만으로 제품 빌드·배포·전체 테스트를 요구하지 않습니다.
사용 가능한 도구로 바뀐 문서의 표시·링크·철자를 확인합니다. 실제 독자의 이해·성공이나 확인하지 않은 구현·환경까지 검증했다고 쓰지 않습니다.
Markdown을 코드 블록으로 보여줄 때는 바깥 울타리를 안쪽의 가장 긴 울타리보다 길게 씁니다(안쪽 백틱 3개 → 바깥 4개 이상). 여닫는 짝과 내부 코드의 경계를 확인합니다.

결과에는 바뀐 문서와 보존한 핵심 조건, 실제 확인 방법·결과, 미실행 예제·미확인 계약을 구분해 보고합니다.
