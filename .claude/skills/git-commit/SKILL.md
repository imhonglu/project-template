# Git 커밋

메시지만 요청받으면 초안을 제공합니다. 커밋 생성·푸시·기존 커밋 수정은 각각 요청받은 경우에 수행합니다.

## 메시지 작성

제공된 변경 내용이나 작업 트리·스테이징을 근거로 한글 개조식으로 요약합니다.
저장소의 별도 규칙을 따르고, commitlint가 있으면 작성한 메시지를 검사합니다.

```text
refactor(api): 응답 변환 로직 통합

- 호출부의 중복 변환을 공통 함수로 이동
- 기존 응답 형식 유지
```

- 제목은 `type(scope): 요약` 형식이며, `scope`는 패키지·영역을 구분할 때 붙입니다.
- 요약은 `추가`, `수정`, `제거`, `정리` 등 한글 개조식으로 작성하고 끝에 마침표를 붙이지 않습니다. 영문 고유명사·코드 식별자는 원래 표기를 유지합니다.
- 제목·본문·꼬리말은 줄마다 100자 이내로 작성하고, 본문·꼬리말 앞에는 빈 줄을 둡니다.

| 유형       | 용도                               |
| ---------- | ---------------------------------- |
| `feat`     | 기능 추가                          |
| `fix`      | 오류 수정                          |
| `docs`     | 문서 변경                          |
| `style`    | 동작에 영향을 주지 않는 서식 변경  |
| `refactor` | 기능·오류 수정 없이 코드 구조 변경 |
| `perf`     | 성능 개선                          |
| `test`     | 테스트 추가·수정                   |
| `build`    | 빌드·의존성 변경                   |
| `ci`       | CI 설정 변경                       |
| `chore`    | 기타 개발 환경·관리 작업           |
| `revert`   | 기존 커밋 되돌리기                 |

### 호환성 변경

호환성이 깨지는 변경은 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시하고 변경 내용과 전환 방법을 설명합니다.

```text
feat(api)!: 목록 응답 형식 변경

BREAKING CHANGE: 배열 응답을 items 필드가 있는 객체로 변경
호출부에서 응답 배열 대신 response.items 참조 필요
```

## 커밋 단위

커밋은 변경의 목적과 의도에 따라 나누고, 각 커밋을 독립적으로 검토·되돌릴 수 있게 구성합니다.
사용자가 지정한 범위·단위를 우선하며, “스테이징한 변경”은 현재 인덱스 안에서 나눕니다.

| 변경의 목적·관계                         | 처리·예                                                      |
| ---------------------------------------- | ------------------------------------------------------------ |
| 목적이 다른 변경                         | 별도 커밋: 기능 추가 / 타입 검사 설정 정리                   |
| 한 목적에 필요하며 함께 검증·되돌려야 함 | 한 커밋: API 계약·호출부·회귀 테스트·문서 / 스킬 원본·배포본 |

## 커밋 생성

1. 작업 트리·스테이징에서 요청 범위를 확인하고 커밋별 목적·내용·의존 순서를 알립니다. 범위가 불명확하면 질문합니다.
2. 잠금 파일·생성물은 해당 커밋의 원본으로 재생성합니다.
3. 기존 스테이징·부분 스테이징을 보존하며 대상 변경 조각만 반영합니다. 범위 밖의 스테이징은 별도 인덱스 등으로 분리합니다.
4. 스테이징 diff에서 목적·포함 파일을 확인하고 비밀값·로컬 환경 파일을 제외합니다.
5. 각 커밋에 담길 상태를 검사합니다. 부분 스테이징은 격리된 작업 디렉터리에서 검증할 수 있습니다.
6. 메시지를 확정하고 Git 훅을 거쳐 커밋합니다. 훅이 파일을 수정하면 스테이징 범위·관련 검사를 다시 확인합니다.
7. 푸시도 요청받았다면 브랜치·원격 대상을 확인한 뒤 푸시합니다.

## 결과 확인

- 커밋 후 새 HEAD 기준으로 남은 스테이징·작업 트리를 확인하고 해시·메시지와 함께 보고합니다.
- 검증한 대상이 작업 트리인지 커밋 내용인지 밝히고, 미검증 범위와 기존 실패·새 실패를 구분합니다.
