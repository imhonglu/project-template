# Git 커밋

메시지만 요청받으면 초안을 제공합니다. 커밋 생성·푸시·기존 커밋 수정은 각각 요청받은 경우에 수행합니다.

## 사용 시점

- 메시지 작성: "커밋 메시지를 작성해줘"
- 형식·유형 검토: "이 메시지를 Conventional Commits 형식으로 다듬어줘"
- 본문·호환성 변경 설명: "BREAKING CHANGE를 어떻게 표시해?"
- 커밋 생성: "기능 구현 후 커밋까지 해줘"

## 작업 절차

1. 작업 트리와 스테이징 범위를 확인하고, 실제 포함할 변경으로 메시지를 작성합니다.
2. 커밋을 요청받으면 해당 변경만 스테이징하며, 기존 스테이징과 부분 스테이징을 보존합니다.
3. 커밋할 때는 저장소 검사와 Git 훅을 적용합니다. 이번 변경으로 생긴 실패는 해결하고, 훅이 파일을 수정하면 스테이징 범위와 관련 검사를 다시 확인합니다.

### 메시지 형식

Conventional Commits 형식과 한글 개조식 요약을 사용합니다. 대상 저장소에 별도 규칙이나 commitlint 설정이 있으면 함께 확인해 적용합니다.

```text
type(scope)!: 한글 개조식 요약
```

- `type`은 아래 소문자 유형을 사용합니다. `scope`는 패키지·영역을 구분할 때, `!`는 호환성이 깨질 때만 붙입니다.
- 요약은 `추가`, `수정`, `제거`, `정리` 등 한글 개조식으로 작성하고 끝에 마침표를 붙이지 않습니다. 영문 고유명사·코드 식별자는 원래 표기를 유지합니다.
- 제목은 유형·범위를 포함해 100자 이내로 작성합니다. 본문·꼬리말이 있으면 앞에 빈 줄을 둡니다.
- 호환성이 깨지는 변경은 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시하고 변경 내용과 전환 방법을 설명합니다.

| 유형       | 용도                               |
| ---------- | ---------------------------------- |
| `feat`     | 기능 추가                          |
| `fix`      | 오류 수정                          |
| `docs`     | 문서 변경                          |
| `style`    | 동작에 영향을 주지 않는 서식 변경  |
| `refactor` | 기능·오류 수정 없이 코드 구조 변경 |
| `perf`     | 성능 개선                          |
| `test`     | 테스트 추가·수정                   |
| `build`    | 빌드·의존성 변경                   |
| `ci`       | CI 설정 변경                       |
| `chore`    | 기타 개발 환경·관리 작업           |
| `revert`   | 기존 커밋 되돌리기                 |

### 메시지 예시

**본문 포함**

```text
refactor(api): 응답 처리 함수 분리

- 중복 응답 처리 로직 통합
- 호출부에서 공통 함수 사용
```

**호환성 변경**

```text
feat(api)!: 목록 응답 형식 변경

BREAKING CHANGE: 배열 응답을 items 필드가 있는 객체로 변경
호출부에서 응답 배열 대신 response.items 참조 필요
```

## 결과 확인

- 메시지의 변경 내용·형식을 확인하고, commitlint가 구성되어 있으면 검사합니다.
- 커밋을 생성한 경우 해시·메시지·남은 작업 트리 상태를 보고합니다.
- 검증 결과와 남은 제약을 보고하고, 이번 변경으로 생긴 실패와 기존 문제를 구분합니다.
