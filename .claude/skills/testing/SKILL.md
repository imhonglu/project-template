# 테스트 설계·작성

작성·실행에는 기존 테스트 도구와 실행 환경을 사용합니다. 아래 API 예제는 Vitest 기준입니다.
Vitest 예제를 적용할 때는 [공식 문서 색인](https://vitest.dev/llms.txt)에서 필요한 기능을 찾아 설치 버전의 동작과 대조합니다.

## 작업별 기준

### 범위·파일 선택

요구사항·공개 계약에서 정상·경계·실패 사례와 실행 환경을 정하고 기존 테스트와 대조합니다.
검증 계획에는 사례별 입력·조건, 기대 결과, 실제로 사용할 의존성과 격리 방법을 담습니다.

| 확인할 동작                  | 파일명 예                             | 읽을 예제                                      |
| ---------------------------- | ------------------------------------- | ---------------------------------------------- |
| 계산·분기·상태 전이          | `get-shipping-fee.test.ts`            | [유닛 테스트](references/unit-tests.md)        |
| 저장·조회, 모듈·DB·HTTP 연동 | `save-note.integration.test.ts`       | [통합 테스트](references/integration-tests.md) |
| DOM·이벤트·브라우저 API      | `create-cart-counter.browser.test.ts` | [브라우저 테스트](references/browser-tests.md) |

- 테스트는 검증할 구현 가까이에 둡니다. 같은 대상·실행 환경은 한 파일에 모으되 책임·격리·실행 비용이 달라지면 나눕니다.
- `.ts`·`.tsx`·`.test`·`.spec` 등 확장자·접미사는 코드 형식과 실행 도구에 맞춥니다.
- 브라우저 프로젝트의 실행 모드와 테스트 파일의 `include`·`exclude`를 확인합니다.

### 작성 예제

[유닛 테스트 예제](references/unit-tests.md)의 `get-shipping-fee.ts`를 검사하는 최소형입니다. 경계·실패 사례는 참고 문서의 테스트로 확장합니다.

```ts
// get-shipping-fee.test.ts
import { expect, it } from "vitest";

import { getShippingFee } from "./get-shipping-fee.ts";

it("무료 배송 기준에 도달하면 배송비가 없습니다", () => {
  const orderTotal = 30_000;

  const fee = getShippingFee(orderTotal);

  expect(fee).toBe(0);
});
```

- `describe`는 대상, `it`은 조건과 결과를 나타냅니다. 준비·실행·검증은 빈 줄로 구분합니다.
- 입력만 달라지면 `it.each`·`it.for`를, 시나리오가 다르면 별도 `it`를 사용합니다.
- 한 테스트는 하나의 시나리오를 다루고, 그 결과를 확인하는 단언은 함께 둡니다.

### 준비·격리

검증하는 경계는 실제 구현을 사용하고 범위 밖 의존성만 필요에 따라 대체합니다.
시간·난수는 재현 가능한 값이나 시드로 통제하고, 가변 입력·모킹·DB·파일·포트는 사례별로 격리합니다.
자원을 얻으면 수명에 맞는 정리를 등록하며, 준비 실패와 종료 실패에서도 실제 회수 여부를 확인합니다.

| 필요한 처리                               | 참고할 기준·예제                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 테스트 본문에서 Disposable 자원 사용 완료 | `using`·`await using`; [파일 I/O 예제](references/integration-tests.md#실제-파일에-저장한-메모-다시-읽기) |
| 공통 준비·공유 자원·정리 순서             | [수명과 훅 선택](references/integration-tests.md#수명과-훅-선택)                                          |
| 비동기 응답의 완료 순서                   | [보류 Promise 예제](references/mocking.md#응답-완료-순서-제어)                                            |
| 함수·모듈·시간 대체                       | [모킹](references/mocking.md)                                                                             |

[`concurrent`](https://vitest.dev/guide/parallelism.html#test-parallelism)는 공유 상태를 바꾸지 않는 테스트에 사용하고 콜백의 `{ expect }`로 단언합니다.
전역 모킹·가짜 시계를 변경하는 사례는 함께 실행하지 않습니다.

### 공통 준비와 도우미

검증 경계·상태 소유자·수명이 같은 준비를 묶습니다.
사례의 입력·응답·옵션·단언은 테스트에 남기며, 실패를 검증할 입력도 그대로 전달합니다.

| 반복되는 내용               | 처리                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------- |
| 의존성·인증·클라이언트 연결 | 사례마다 독립된 상태를 만드는 팩토리                                                              |
| 모듈 모킹·환경별 정리       | [등록 시점과 수명을 명시한 훅](references/mocking.md#공유-모킹의-등록과-초기화) 또는 `setupFiles` |
| DOM·조회 캐시               | [렌더링과 정리](references/browser-tests.md#공통-렌더링과-정리)를 함께 소유                       |

#### 준비 코드의 배치

| 준비의 사용 범위                   | 배치                          |
| ---------------------------------- | ----------------------------- |
| 한 파일에서만 쓰는 준비            | 해당 테스트 파일 안           |
| 재사용 도우미                      | 소유 영역의 `testing/`        |
| 독립 실행할 테스트용 자식 프로그램 | 가까운 `fixtures/<프로그램>/` |

### 단언 선택

호출자가 관찰할 반환값·오류·상태 변화·부수 효과를 검증합니다.
기대값은 요구 계약에서 구하며, 구현의 수식·상수·실제 출력을 복사해 만들지 않습니다.

설정·내부 구조는 적용 후 동작으로 검증하되, 값 자체가 계약이면 직접 단언합니다.

| 항목           | 기준                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| 원시값·동일성  | `toBe`; 객체·배열의 정확한 구조는 `toStrictEqual`                                                         |
| 부분 계약      | 관심 있는 공개 필드만 검증할 때 `objectContaining`                                                        |
| 오류           | 동기 `expect(() => run()).toThrow(...)`; 비동기 `await expect(run()).rejects.toThrow(...)`                |
| 비동기 결과    | `resolves`·`rejects`·브라우저 단언과 사용자 조작은 `await`                                                |
| 상태 변화 대기 | 완료 Promise는 직접 `await`; 관찰해야 하는 상태는 `await expect.poll(...)`                                |
| 호출 검증      | 외부 API에 전달할 값처럼 호출 자체가 계약일 때 `toHaveBeenCalledWith`                                     |
| 타입 검증      | 일반 테스트에 [expectTypeOf](references/type-tests.md)를 작성하고 테스트 파일을 포함한 `typecheck`로 검사 |
| 스냅샷         | 작고 안정적인 출력에 사용하며 갱신 시 차이를 직접 검토                                                    |

[`expect.poll`](https://vitest.dev/api/expect.html#poll)은 콜백을 재시도하므로 조회만 수행합니다. 브라우저 화면은 `expect.element`로 기다립니다.

테스트의 이름·호출·단언을 사용 예제로 삼고, 주석에는 코드에서 드러나지 않는 설정 이유·실행 제약을 적습니다.

### 실패 분석·회귀 검증

가장 작은 재현 사례부터 시작하고, 그 검사로 확인할 수 없는 경계만 실제 의존성으로 검증합니다.
원격 서비스·배포물은 [실제 환경과 배포물](references/integration-tests.md#실제-환경과-배포물)의 조건을 확인합니다.

| 확인한 원인                  | 조치                                             |
| ---------------------------- | ------------------------------------------------ |
| 요구사항 변경                | 새 계약에 맞춰 기대값 갱신                       |
| 구현 결함                    | 재현 입력으로 수정 전 실패·수정 후 통과 확인     |
| 실행 순서·시간에 따라 달라짐 | 공유 상태·대기 조건·미완료 작업 확인             |
| 단언이 결함을 잡는지 불명확  | 격리된 사본에서 관련 분기를 바꿔 실패하는지 확인 |

수정 전 재현을 확인하지 못했으면 미확인으로 보고합니다. 통과를 위한 단언 완화·임의 대기·재시도·`skip`은 추가하지 않습니다.

## 결과 확인

### 검증 계획

- 각 사례의 기대 결과가 요구 계약에서 나오며, 선택한 검증 경계에서 관찰 가능한지 확인합니다.
- 준비·격리·종료 방법과 실제 환경에서만 확인할 수 있는 범위를 구분합니다.

### 테스트 변경

- 테스트 파일이 프로젝트의 실행·타입 검사 대상에 포함됐는지 확인합니다.
- 제목·입력·단언에서 검증하는 동작을 바로 파악할 수 있는지 확인합니다.
- 공통화 전후의 사례·단언·타입 추론을 대조하고, 변경한 격리·자원 회수·훅 순서를 검증합니다.
- `test`·`typecheck`를 포함한 최종 검사를 실행합니다. 전체 `check`가 있으면 이를 사용하고 포함된 단계는 중복 실행하지 않습니다.
- 커버리지 보고서가 있으면 변경한 분기·오류 경로와 실제 단언을 대조해 누락을 확인합니다.
- 실행한 검사·결과와 미실행·미확인 범위를 구분해 보고합니다.
