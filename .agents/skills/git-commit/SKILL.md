# Git 커밋

메시지만 요청받으면 초안을 제공합니다. 커밋 생성·푸시·기존 커밋 수정은 각각 요청받은 경우에 수행합니다.

## 메시지 작성

제공된 변경 내용이나 작업 트리·스테이징을 근거로 한글 개조식으로 요약합니다. 저장소의 별도 규칙·commitlint 설정도 함께 적용합니다.

```text
refactor(api): 응답 처리 함수 분리

- 중복 응답 처리 로직 통합
- 호출부에서 공통 함수 사용
```

- 제목은 `type(scope): 요약` 형식입니다. `type`은 아래 소문자 유형을 사용하고, `scope`는 패키지·영역을 구분할 때 붙입니다.
- 요약은 `추가`, `수정`, `제거`, `정리` 등 한글 개조식으로 작성하고 끝에 마침표를 붙이지 않습니다. 영문 고유명사·코드 식별자는 원래 표기를 유지합니다.
- 제목과 본문·꼬리말의 각 줄은 100자 이내로 작성합니다. 제목 길이에는 유형·범위도 포함하며, 본문·꼬리말 앞에는 빈 줄을 둡니다.

| 유형       | 용도                               |
| ---------- | ---------------------------------- |
| `feat`     | 기능 추가                          |
| `fix`      | 오류 수정                          |
| `docs`     | 문서 변경                          |
| `style`    | 동작에 영향을 주지 않는 서식 변경  |
| `refactor` | 기능·오류 수정 없이 코드 구조 변경 |
| `perf`     | 성능 개선                          |
| `test`     | 테스트 추가·수정                   |
| `build`    | 빌드·의존성 변경                   |
| `ci`       | CI 설정 변경                       |
| `chore`    | 기타 개발 환경·관리 작업           |
| `revert`   | 기존 커밋 되돌리기                 |

### 호환성 변경

호환성이 깨지는 변경은 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시하고 변경 내용과 전환 방법을 설명합니다.

```text
feat(api)!: 목록 응답 형식 변경

BREAKING CHANGE: 배열 응답을 items 필드가 있는 객체로 변경
호출부에서 응답 배열 대신 response.items 참조 필요
```

## 커밋 생성

커밋을 요청받은 경우 다음 순서로 진행합니다.

1. 작업 트리·스테이징 내용을 확인하고 요청받은 변경을 스테이징합니다.
   - 기존 스테이징과 부분 스테이징을 보존합니다.
   - 비밀값·로컬 환경 파일은 제외하고, 잠금 파일·생성물은 원본 변경과 함께 포함합니다.
2. 저장소 검사를 실행하고 이번 변경으로 생긴 실패를 해결합니다.
3. 실제 스테이징한 변경에 맞춰 메시지를 확정하고 커밋합니다.
   - Git 훅을 임의로 우회하지 않습니다.
   - 훅이 파일을 수정하면 스테이징 범위와 관련 검사를 다시 확인합니다.
4. 푸시도 요청받았다면 브랜치·원격 대상을 확인한 뒤 푸시합니다.

## 결과 확인

- 메시지의 변경 내용·형식을 확인하고, commitlint가 구성되어 있으면 검사합니다.
- 커밋을 생성한 경우 해시·메시지·남은 작업 트리 상태를 보고합니다.
- 검증 결과와 남은 제약을 보고하고, 이번 변경으로 생긴 실패와 기존 문제를 구분합니다.
