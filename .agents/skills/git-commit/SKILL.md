# Git 커밋

요청 범위의 상태·diff·규칙 파일처럼 독립적인 조회는 한 호출에 묶고, 판단에 부족한 근거만 추가로 확인합니다.

| 요청             | 수행할 작업                                                 |
| ---------------- | ----------------------------------------------------------- |
| 메시지 작성·추천 | 초안만 제공; 파일·인덱스 유지                               |
| 커밋 생성        | 요청 범위로 새 커밋 생성                                    |
| 특정 커밋 재작성 | 지정한 메시지·내용만 수정; “마지막 커밋 메시지 고쳐줘” 포함 |
| 푸시             | 지정한 원격·대상 반영                                       |

커밋·재작성·푸시는 각각 명시적 요청이 필요합니다. 재작성이나 일반 푸시 요청은 강제 푸시를 허용하지 않습니다.

## 메시지 작성

요청 대상 diff를 한글 개조식으로 요약합니다. “스테이징한 변경”은 인덱스만, 특정 커밋은 해당 커밋만 대상으로 합니다.
저장소의 형식·길이 규칙을 우선하며, commitlint가 있으면 초안도 검사합니다. 실행 결과 또는 미실행 이유를 밝힙니다.

```text
refactor(api): 응답 변환 로직 통합

- 호출부의 중복 변환을 공통 함수로 이동
- 기존 응답 형식 유지
```

- 제목은 `type(scope): 요약` 형식이며, `scope`는 패키지·영역을 구분할 때 붙입니다.
- 요약은 `추가`, `수정`, `제거`, `정리` 등 한글 개조식으로 작성하고 끝에 마침표를 붙이지 않습니다. 영문 고유명사·코드 식별자는 원래 표기를 유지합니다.
- 제목·본문·꼬리말은 줄마다 100자 이내로 작성하고, 본문·꼬리말 앞에는 빈 줄을 둡니다.

| 유형       | 용도                                    |
| ---------- | --------------------------------------- |
| `feat`     | 기능 추가                               |
| `fix`      | 오류 수정                               |
| `docs`     | 문서 변경                               |
| `style`    | 동작에 영향을 주지 않는 서식 변경       |
| `refactor` | 기능 추가·오류 수정 없이 코드 구조 변경 |
| `perf`     | 성능 개선                               |
| `test`     | 테스트 추가·수정                        |
| `build`    | 빌드·의존성 변경                        |
| `ci`       | CI 설정 변경                            |
| `chore`    | 기타 개발 환경·관리 작업                |
| `revert`   | 기존 커밋 되돌리기                      |

### 호환성 변경

호환성이 깨지는 변경은 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시하고 변경 내용과 전환 방법을 설명합니다.

```text
feat(api)!: 목록 응답 형식 변경

BREAKING CHANGE: 배열 응답을 items 필드가 있는 객체로 변경
호출부에서 응답 배열 대신 response.items 참조 필요
```

## 커밋 단위

독립적으로 검토·되돌릴 수 있는 목적별로 나누고, 그 목적의 계약·호출부·테스트·문서·생성물을 묶습니다. 분리하면 계약이 깨지는 변경은 함께 유지합니다.
사용자가 정한 범위·단위를 우선하며 같은 파일의 다른 목적은 조각으로 나눕니다. “스테이징한 변경”은 현재 인덱스 안에서만 나눕니다.

## 커밋 생성·재작성

훅의 검사·자동 수정·스테이징 반영 방식을 먼저 확인합니다.

1. 요청 대상 diff에서 커밋별 목적·파일·조각·의존 순서를 정해 알립니다. 제공된 근거로 포함 범위를 정할 수 없을 때만 질문합니다.
2. 필요한 생성물은 도구로 재생성해 같은 목적의 커밋에 넣습니다. “스테이징한 변경만” 요청에 생성물이 빠졌다면 파일·이유를 알리고 범위를 확인합니다.
3. 대상 조각만 스테이징해 기존 부분 스테이징을 보존합니다. 범위 밖의 기존 인덱스는 되돌리지 않고 별도 인덱스·격리 디렉터리로 분리합니다.
4. 최종 인덱스가 요청 범위와 같은지 대조합니다. 비밀값·로컬 환경 파일이 있으면 커밋을 멈추고 알립니다. 사용자 파일을 삭제하거나 범위 밖 스테이징을 해제하지 않습니다.
5. 커밋에 담길 상태로 필요한 검사를 실행합니다. 미스테이징 변경이 결과에 영향을 주면 격리된 디렉터리에서 인덱스를 검사합니다.
6. 훅을 활성화해 커밋하고 요청 조각·부분 스테이징의 보존 여부를 확인합니다. 실패를 우회하거나 원인을 해결하지 않은 채 자동 재시도하지 않습니다.

훅이 수정하면 바뀐 상태에서 영향받는 검사를 다시 실행합니다. 훅의 스테이징을 파일 전체 추가로 덮지 않으며, pre-commit 성공을 전체 검사 성공으로 대신하지 않습니다.
메시지만 재작성할 때는 기존 스테이징을 새 내용에 넣지 않습니다.

## 푸시

현재 브랜치·원격·대상을 확인한 뒤 요청한 대상에만 푸시합니다.

## 결과 확인

- 메시지만 작성했다면 이미 읽은 diff를 근거로 초안·변경 범위·메시지 검사 결과를 보고합니다.
- 커밋했다면 새 HEAD와 검증한 상태의 일치 여부, 남은 스테이징·작업 트리를 확인하고 해시·메시지와 함께 보고합니다.
- 미검증 범위와 기존 실패·새 실패를 구분합니다.
